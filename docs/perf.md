# 性能基准与优化记录

本文记录 FlashDir 的**可复现性能基准**、每项优化的前后对比，以及测量口径上的坑。
所有数字都在 release 下、用本机真实数据测得，不使用合成数据（除注明者）。

## 1. 怎么跑

```powershell
cd src-tauri

# 单元测试（含正确性回归）
cargo test --lib

# 基准：全部 ignored 基准
cargo test --release --lib -- --ignored --nocapture bench

# ⚠️ 基准必须**按名字单独跑**：
#    测试框架会并行执行多个 ignored 基准，彼此争抢 CPU/磁盘/页缓存，数字会互相污染
#    （实测同一基准并行跑时 load_global_index 从 2.3s 变成 14.5s）。
cargo test --release --lib -- --ignored --nocapture bench_search_pagination
cargo test --release --lib -- --ignored --nocapture bench_real_global_search
cargo test --release --lib -- --ignored --nocapture bench_blob_disk_form
cargo test --release --lib -- --ignored --nocapture bench_index_io_does_not_block_dir_cache
```

### 测量口径（务必先读，否则会得出错误结论）

| 事项 | 说明 |
|---|---|
| 串行 vs 并行 | 基准里手写的 A/B 循环是**串行逐条**；而真实查询 `search_internal` 走 rayon 并行（本机约 8×）。两者**不能直接比较**：串行 800ms ≈ 查询级 100ms。 |
| 页缓存冷热 | 同一份 370MB blob：热页缓存读取 ~100ms，冷页缓存（重启后首次）**~17.2s**。跨机器/跨次比较必须说明冷热。 |
| 单次运行波动 | 同机重复测量波动可达 ±20~30%（例：`dir:windows` 出现过 90ms 与 118ms）。判定优化是否成立要看**同一批次内的 A/B**，不要拿不同批次的两个数对比。 |
| 索引在被并发修改 | 桌面端在运行时其后台线程每 5 分钟做一次 USN 增量同步，会**持续改写持久化索引**。实测同一台机器上索引条目数在几十分钟内从 3,104,835 漂到 3,106,896。要拿到可比数字，要么确认桌面端已退出，要么接受条目数会变并在报告里注明。 |
| K 的影响 | top-K 的 K 直接决定"命中数百万条"时的成本，见下表。**为后续翻页预先放大 K 是错的**（曾因此让首屏 24ms→155ms）。 |

## 2. 优化前后对比

### 2.1 检索（global_search）

| 场景 | 优化前 | 优化后 | 备注 |
|---|---|---|---|
| 连续加载 10 页（每页 1000） | 215 ms | **1.16 ms** | 新增按索引代次失效的查询结果缓存 |
| 越界翻页 offset=5万 / 20万 | 21.7 / 21.8 ms | **600 ns / 200 ns** | 缓存已含全部命中 |
| 首屏单页 | 20.1 ms | 23.5 ms | 缓存 miss 那一次的代价（+17%），换后续翻页免费 |
| `report*`（首字符桶快路径） | 3.6 ms | 3.6–13 ms | 分桶设计本身有效；数字波动大 |
| 全量扫描地板（条件永不命中） | 24.4 ms（**口径错误**） | **7.8–8.3 ms** | 旧基准写的是 `size:>1PB`，而单位只支持到 TB → 未知单位被当 1 字节，实际匹配了全部条目，测的根本不是地板 |
| CJK 包含匹配（3,104,860 条） | 509.9 ms | **318.2 ms（−37.6%）** | 去掉逐条 `to_lowercase` 分配；另两次运行 424.5→306.8、372.4→264.3 |
| ASCII 路径包含（`dir:`/`PathText` 热点，串行） | 789–829 ms | 待 `path_ascii` 落地后逼近 **510 ms** 下限 | 窗口扫描 510ms 是下限；差额来自每条路径一次 `is_ascii()` 全串扫描 |
| 索引内存构建（3,104,862 条） | 2.2687 s | **0.6630 s（−70.8%）** | 并行构建 `by_path`/`name_index` + 预分配 arena |

K 敏感度（命中 310 万条的查询，实测）：

| K | 耗时 |
|---|---|
| 500 | 21.7–28 ms |
| 5,000 | 74.5–88.7 ms |
| 50,000 | 244.5–282 ms |

### 2.2 目录缓存与索引持久化（disk_cache / scan）

| 场景 | 优化前 | 优化后 | 备注 |
|---|---|---|---|
| blob 体积（`C:/`，193 万条） | 388,594,345 B | **308,364,528 B（−20.6%）** | 只落盘不可派生字段（`BLOB_VERSION` 2→3） |
| blob 解码（同批 193 万条，取最小值） | 818.5 ms | **545.8 ms（−33.3%）** | 含 rayon 并行派生 `name`；并行 38.1ms vs 顺序 349.6ms |
| blob 原始读取 370.6 MB | 冷 17.2 s / 热 100 ms | 未变（分片是下一步） | 磁盘带宽瓶颈 |
| 索引载入期间目录缓存延迟 | 旧单锁最大 1491 ms | **最大 0.2 ms / 平均 0.011 ms**（112,736 次采样） | 索引改用独立 SQLite 连接；旧值由临时绕过索引连接测得 |
| `load_global_index` 310 万行 | 2.55 s | 2.47 s（−3.1%） | 微优化，收益有限 |

> `BLOB_VERSION` 升到 3 后，磁盘上旧的 v2 blob 会被版本校验判为未命中 →
> **每个目录首次访问会重扫一次**并写成新格式。这是有意取舍（避免写迁移代码）。

### 2.3 索引常驻内存（P2 内存局部性的 before 基线）

`bench_index_memory`（3,105,150 条，逻辑占用，不含分配器元数据）：

| 组成 | 占用 | 每条约 |
|---|---|---|
| arena（`size_of::<IndexEntry>()` = 72B） | 213.2 MB | 72 B |
| `path` 的 String capacity | **349.8 MB** | 118 B |
| `name_lower` 的 String capacity | 75.9 MB | 26 B |
| **合计（逻辑）** | **638.9 MB** | **216 B** |

- 分配器元数据另计：每条约 3 个分配块（arena 批量分配 + 2 个 String），
  mimalloc 每块约 16B 头 → 约 48 B/条，即再 +150 MB 量级。
- **路径本身占了一半以上**（350/639 MB），这正是"目录前缀驻留"的优化空间：
  同一目录下的条目共享长前缀，改成 `(目录 id: u32, 文件名)` 理论上能省下大部分，
  但 `entry.path` 被过滤、`is_same_or_child`、前缀删除、blob 往返、前端序列化
  等大量代码直接消费，属深度重构，需要独立一轮。
- `name_lower` 按需派生可省 75.9 MB，但它是 `Text`/`Name` 过滤的热路径（每条目都要
  `contains`），改成每次重算会拖慢查询 —— **不建议**为省内存牺牲查询速度。
- **非 ASCII 路径 164,215 条（5.3%）**：这 5.3% 就是 `contains_ignore_case` 里
  Unicode 折叠回退（`to_lowercase()`）无法移除的原因 —— 移除会让西里尔/土耳其语
  等路径漏掉命中。实测这部分回退占 `dir:` 类查询成本约 71ms（见 2.1 与第 3 节）。

**已落地：`name_lower` 改用内联 `CompactString`**（`SmartString<Compact>`，内联 ≤23 字节）。
`name_lower` 是小写文件名（通常远短于路径），原本为每条做一次堆分配；`CompactString` 与
`String` 同为 24 B，所以内联收益**不换来 arena 膨胀**（有断言测试钉住 `<=72B`）：

| 指标 | 前 | 后 |
|---|---|---|
| `size_of::<IndexEntry>()`（arena） | 72 B | **72 B（零代价）** |
| `name_lower` 堆占用 | 123.6 MB | **73.7 MB（−40.4%）** |
| 堆口径合计（含 16 B/块分配器头） | 735.7 MB | **686.2 MB（−49.9 MB ≈ −6.8%）** |
| 内联命中率 | — | **68.6%**（2,138,284/3,116,328） |

文本查询（12 before / 18 after 样本均值）：`report` −11.8%、`ab` −10.2%、`node_modules`
−10.8%、`readme.md` −10.1%、`*.pdf` −19.2%、`ext:zip size:>10MB` −15.3%；
对照组（不碰 `name_lower`）`size:>1GB` +0.5%、`dir:windows` +1.4% → 提速不是全局漂移。

**口径提醒**：内联 `CompactString` 的 `.capacity()` 恒返回 23（MAX_INLINE），与 `String`
不可比。因此 `bench_index_memory` 现在**同时打印两种口径**（裸 capacity 与堆分配字节数），
判断收益只看**堆口径**（否则会看到"内存反而涨了"的假象）。

## 3. 被实测证伪的尝试（不要重复）

| 尝试 | 结果 | 原因 |
|---|---|---|
| 给字节窗口匹配加"首字节大小写两态定位" | **828 ms**（比原 510 ms 更慢） | needle 首字节 `w` 在 Windows 路径里极常见，过滤率低；逐位置分支还引入不可预测跳转。std 的 `windows().any(eq_ignore_ascii_case)` 已足够好。 |
| `Vec::with_capacity(COUNT(*))` 预分配索引 Vec | 未采用 | `COUNT(*)` 自身 0.5s，大于省下的搬运开销 |
| SQLite `mmap_size=2GB` + `cache_size=256MB` | 无收益（3.0–3.6s 噪声内） | — |
| `path` 也改成 `CompactString`（或 `Box<str>`） | 否决（省不下任何东西） | 实测 `path` 的 capacity 合计 **== 长度合计（冗余 0.0%）**，≤23 B 可内联的路径仅 **0.603%**（18,786/3,116,328）→ 换表示无收益，却要在 `format!`/`into_owned()` 等多条生产路径上加转换。路径内存（350 MB，占逻辑占用一半以上）只能靠"目录前缀驻留"解决 |
| `dir:` 加速：段倒排索引 / 逐条位图预过滤 | 否决（典型 needle 1.8x、长路径片段 3.0x；理论上限仅 ~5–6x） | 实测 `dir:windows` 的真实命中率本就占 14.91%（完美索引也只能把候选降到 14.91%）；段倒排需 **33.66M postings / ≥128MB**，且 postings 存 arena 下标后**每次 `swap_remove` 都要修正**（静默错结果的不变式）；4B/条位图正好塞进 `IndexEntry` 现有 padding（零额外内存）但只值 **1.0–1.2x**；8B/条（+23.8MB）才 1.9–3.0x。判据测试已就位：`tests_regression::dir_query_equivalence_under_random_mutations`（随机变异 + 暴力参考对拍，且已验证"有牙"） |

| 项 | 预期 | 风险/前置 |
|---|---|---|

| blob 分片（按子目录，每片 ≤8–16MB） | 冷读 17s → <0.5s；变更不再整块重写 370MB | 落盘格式 + 淘汰粒度 + 迁移，改动最大 |

| USN 增量就地更新 | 单条变更不再重算全部祖先体积、不重写整份 blob | 与 blob 分片联动 |
| `global_index` 4 个只写不读列（约 496MB） | 表 −24.6%、库 −19.3%、载入 −14.5% | **已并入 main**，见 4.1 |

### 4.1 已并入：`global_index` schema 收拢（迁移移到"重建索引"路径）

复核确认 `name`/`ext`/`drive`/`created_at` 在 `global_index` 上无任何生产读取方
（`name_lower` 亦已改为由 `path` 派生），因此收拢为 `path, size, is_dir, mtime`。
在**真实库的副本**上实测（`FLASHDIR_CACHE_DB` 指向副本，真实库全程只读）：

| 指标 | 迁移前 | 重建后(未 VACUUM) | +VACUUM |
|---|---|---|---|
| `global_index` 表 | 549.4 MB | 414.5 MB | 414.5 MB（−24.6%） |
| DB 文件 | 995.4 MB | 1854.9 MB（**+86.5%**） | **803.8 MB（−19.3%）** |
| 载入 | 2.269 s | 1.773 s | **1.941 s（−14.5%）** |

**关键发现**：重建表 + 改名**不会**回收文件空间（老表页只进 freelist，SQLite 提交时不
truncate），必须补 `VACUUM`，否则首次迁移会把库从 995MB 撑到 **1.85GB**。

**最终落地方案（消除启动冻结）**：
1. **启动路径只留 `CREATE TABLE IF NOT EXISTS`**：老库上是 no-op（SQLite 只读 schema、
   不碰数据页），实测 `DiskCache::open` 从 **53.3s → 1.31ms**，schema 与 b-tree 根页均未变。
2. **写路径按列集合自适应**（每实例探测一次并缓存）：老库照 9 列写、新库只写 4 列，
   调用方语义不变 —— 因此老库**不迁移也能继续读写**，启动期不再需要迁移。
3. **收拢搬到 `save_global_index_stream`**（用户主动"重建索引"才会走到）：该函数本就要
   清空整表全量重灌，直接 DROP + CREATE 即可（无需拷 9 列），DDL 参与事务可整体回滚；
   提交后事务外补 VACUUM。

**当初不并入的原因，及其解决情况**：
1. ~~42s 窗口冻结~~ → **已解决**（启动 1.31ms，且不动老库 schema）。
2. **不可逆**（仍存在）：收拢后无回滚路径，恢复只能删库重建整份索引。
3. **破坏降级**（仍存在）：收拢后旧构建（≤3.5.1）的索引写入会失败（其 INSERT 显式列出
   被删掉的列），表现为"持久化失败"日志 + 索引不再落盘，内存搜索不受影响。属本项目既有
   做法（3.5.0 已发生过磁盘缓存格式变更），但必须写进版本说明。
4. ~~启动期 2.7GB 峰值~~ → 已推迟到重建路径（用户主动触发）。

**建议改造方向**：迁移放后台线程 + 迁移完成前暂缓索引写入（或让写入按表结构自适应、
永不迁移，只在新建库/用户主动重建索引时使用新 schema），并把 VACUUM 延后到空闲时。
| 索引重建单事务期间的 `SQLITE_BUSY` | 消除目录缓存写失败 | 需分块事务（牺牲重建原子性）或调大 busy_timeout，属产品取舍 |
